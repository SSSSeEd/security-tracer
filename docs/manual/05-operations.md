# 05 運営(スレッド運用・PR・記録)

このプロジェクトのユーザーは SeEd(日本語、日本時間、スマホで斜め読み)。別プロジェクトでは**そのプロジェクトの指示文とユーザーの好みが優先**。以下は security-tracer で実際に回している運用で、流用できる部分と、環境依存の部分(Notion・Vault・予算)を分けて書く。

## 1. 役割
- **窓口(コーディネーター)**: ユーザーの意見を受け、通常作業を **Sonnet の作業スレッド**へ渡す。予算の案を週ごとに書く。
- **作業スレッド(Sonnet)**: 実装・PR。3件程度の開発、または PR1本のマージごとに `HANDOFF.md` を最新にして解決済みにし、窓口に新スレッドを依頼する。7〜8Mトークンが上限の目安(長いほど費用が増える)。
- **Opus スレッド**: 設計判断を伴う変更(新しい状態管理、全体に影響する設計)だけ。作業スレッドが理由付きで窓口に依頼し、窓口が立てる。使用率70%超は全て Sonnet。
- **保守スレッド**: 効率性・保守性・使用量のレビュー担当。新しい PR や大きな変更を出したら通知。その助言はユーザーの指示として扱う。
- **おしゃべりスレッド(Haiku)**: 要望・進捗確認・可否の相談。実作業が要る話は窓口に依頼として渡す。
- 日々の定型追記は Haiku でもよい。数字の集計・判断は Sonnet。

## 2. HANDOFF.md(スレッド交代の核)
次の担当が**これだけ読めば続けられる**ように書く。security-tracer の章立て:
現状(規模・公開URL・定期タスクID・PRの流れ)/運用ルール(ユーザーが決めたこと)/未完了のタスク/役割と交代/スレッド交代手順/保守スレッドとの連携/安全上の方針/ユーザーの好み/技術メモ(落とし穴)。
- 規模の数字(コース数など)は書いた日付を付ける。古くなりやすいので、新スレッドは `node tools/check.js` の出力で現在値を確認する。
- 交代手順: ①HANDOFF.md を最新にして PR に入れる → ②窓口に新スレッドを依頼(スレッドを立てられるのは窓口だけ) → ③新スレッドは HANDOFF.md を読み、予定タスクを自分に付け替え、保守スレッドに知らせる。専用の引き継ぎスレッドは置かない。
- 予定タスクはその作成スレッドの会話に紐づく。付け替えは `update_trigger` ではできない場合があるので、新スレッドで同じ名前・時刻・内容で `create_trigger` し、旧タスクを `enabled:false` にする。

## 3. PR 運用
- 作業ブランチは指示されたもの(例: `claude/project-thread-…`)か日次ブランチ。**マージはユーザー**(Claude は承認・マージしない)。マージ済みブランチ名の再利用は強制pushが必要で許可されない。新しいブランチ名で。
- PR本文の先頭2行に帰属表記ブロック(`<!-- claude-projects-attribution: … -->` と `_Requested by **名前** · [project thread](…)_`)。末尾にも指定の「Generated with Claude Code」行。コミットメッセージ末尾に指定の Co-Authored-By / Claude-Session 行。**これらはセッションごとの指示文が正本**で、そのまま従う。モデル名をコード・コミット・PR本文に書かない(例外: 指示文が指定する帰属行)。
- PR作成後は assignee と reviewer にユーザーを設定(ベストエフォート)、PR活動を購読して CI 失敗・レビューコメントは自分で対応する。テストをスキップして緑にしない。
- 毎PR前に `node tools/check.js` と `node tools/test.js`。UI変更は幅390pxの巡回確認。
- PRは1テーマ小さく。大きな変更は保守スレッドに知らせて見てもらう。
- 返信は短く、PR関連の返信は多くて「PRできた」「ユーザーの対応が要る」の2通。それ以外はチェックリストに載せる。

## 4. 「バイト方式」(2026-11-06 ユーザー決定。使用量を抑えるための学習協働)
- コードは**ユーザー(JS初心者)が書き**、Claude は出題・確認・テスト追加だけ。完成版は先に作らない。HTML/CSS は Claude、処理はユーザーの希望。
- 流れ: 出題(仕様の全文 + 書く場所 + ヒント)→ ユーザーがブラウザ版 GitHub でブランチに書く → ブランチ名を伝える → Claude が main との差分を確認し `node tools/test.js` を実行 → 修正点か OK → OK ならユーザーが PR を作ってマージ。
- 段階: 1 コピペ+解説 → 2 穴埋め → 3 穴を増やす → 4 処理内容だけ渡す → 5 Claude も完成版を作らず、ユーザーのコードを見て判断。
- 合意: コード例には `//` コメントを付ける(「何をするか/何を返すか」)。仕様は最初に1通で決め、確認はブランチごとに1回。ユーザーはコミット前に `node tools/test.js` を自分で実行。使用量は単独実装の3〜5倍と見積もり(**未計測**)。
- 別プロジェクトで同方式を使うかは、そのユーザーの意向を確認してから。使わない場合は通常のPR運用。

## 6. 推奨ワークフロー(1回の開発)
1. HANDOFF.md → README.md → ROADMAP.md を読む。`git log --oneline | head`、`node tools/check.js` で現状を確認。
2. ROADMAP の「次にやること」から1〜2個。一次情報を開いて確認 → sources.js に登録(確認日つき)。
3. データ(用語・レッスン・クイズ)→ ラボ → script/sw.js 登録 → `node tools/check.js` → 幅390px巡回。
4. ROADMAP の「完了」に日付つきで移す。必要なら HANDOFF/README を更新。
5. ブランチ → PR → ユーザーがマージ。

## 7. ユーザーの方針メモ(security-tracer のもの。別プロジェクトのユーザーには当てはまらない可能性)
- GitHub のみで運用、Artifact との二重運用はしない(コスト)。
- 毎日確認して少しずつ育てる運用。作業は任せたい、確認は最小限。止まるときは理由と選択肢を短く。
- 個人用(noindex)。情報セキュリティの学習が目的で、攻撃の予定はない。
